Owner: Sonnet implementation agent. Reviewer: independent Opus agent. Source: the phase 5 final audit at commit `170b09c`. Each finding below was reproduced by the auditor, several in a real browser, and survived independent verifiers. The evidence and verifier notes are quoted in full. ## Lead's decisions

1. **Forbidden session (FA-16).**
   - When `host.hello` is refused with `forbidden` (the session belongs to another host account), the host and presenter pages stop: no reconnect, no token refresh.
   - They show a clear screen that names the problem, links to the dashboard and offers sign-out. Add it to the gallery (manifest and registry) for both pages.
   - Separately, token refresh after an auth error is throttled (at most one refresh per reconnect attempt, with the normal backoff), so no error can make a tight loop.
   - Test both in the host state and driver tests. Also add a browser test with the scripted server that counts `host.hello` frames and token calls over a few seconds.
2. **Unsaved changes (FA-17, FA-21).**
   - Browser Back and Forward while the editor has unsaved changes show the same confirmation as the header links. Cancel restores the URL and keeps the edits; Confirm leaves.
   - Sign out while dirty confirms the same way.
   - "Leave and lose changes" when the target is `/edit?q=new` from an unsaved new quiz resets the editor to a fresh quiz.
   - Add browser tests for Back, Sign out and New quiz.
3. **Focus management (FA-18).** No action moves focus to `<body>`:
   - After moderation Show/Hide, focus goes to the same-position item's first action, or to the queue heading when the list is empty.
   - After Kick is confirmed, focus goes to the next roster row's Kick button, or the roster search box if none.
   - Removing an answer focuses the neighbouring answer's input.
   - Moving a question keeps focus on the same button of the moved card.
   - Removing a question focuses the next card's summary, or the add-question control.
   - Assert `document.activeElement` in the browser tests for each case.
4. **Presenter announcements (FA-19, FA-20).**
   - The lobby live region announces the PIN once when the lobby appears.
   - Join announcements carry no PIN, are throttled (no more than one every 10 s) and use correct plurals ("1 player").
   - The control bar is `role="group"` with its label, not `role="toolbar"`. The global keyboard map is unchanged, so a clicker still advances the game when focus is in the bar.
5. **Image alt text (FA-22).**
   - Add an optional `imageAlt` to the question input: a plain string, max `LIMITS.imageAltMax` = 150 characters, trimmed, allowed only with `imageKey`. Pass it through to the presenter's public question.
   - The editor shows an "Image description" field (with counter) whenever an image is set, with a hint to describe the image if the question depends on it.
   - The presenter uses it as `alt`. Without one, the image is decorative (`alt=""`); the prompt next to it is the accessible content.
   - The editor preview's alt follows the same rule.
   - Update protocol, engine and editor tests. Players never receive images, so the player view is unchanged.

6. **Follow-ups from the V2 visual task.** V2 could not do these because it did not own the files.
   - `ui/TextField.module.css` draws the invalid state as a border plus `box-shadow: inset`, which shows as a double line under `prefers-contrast: more`. Replace it with one thicker border and compensating padding, as `AnswerOption`'s chosen state does now. Then delete the scoped overrides in `screens/join/Join.module.css` and `screens/play/TextEntry.module.css`. Check the invalid fields on the join, text-entry, host login and editor screens in the high-contrast and forced-colours screenshots.
   - `revealHeadline('unscored')` in `state/format.ts` uses the same words as the "answer locked in" heading. Give the reveal its own headline, such as "Question closed". The card below already says no points were given. `announce.ts` and `e2e-live/player.ts` follow the function, so update any test that pins the old text.
   - The player reducer (`state/player.ts`) keeps the player's own submission for the current question through its reveal. It is not kept across a resume, because the snapshot does not carry it. The unscored reveal shows it ("Your answer: B · Pizza", or the words or text entered). After a resume it simply shows nothing.

### FA-16 (major) A 'forbidden' host.hello starts an unthrottled Cognito refresh and reconnect loop

- Lens: frontend. Files: `apps/web/src/state/host.ts`, `apps/web/src/screens/host/useHostSession.ts`, `apps/web/src/auth/session.ts`, `packages/service/src/game-service.ts`
- Evidence: state/host.ts:239-241 maps both codes to the same end state: `case 'unauthorized': case 'forbidden': return { ...state, ended: 'unauthorized' };`

useHostSession.ts:102-110 then refreshes and reconnects:

```
if (state.ended !== 'unauthorized') return;
void auth.handleUnauthorized().then((ok) => {
  if (!ok) return;
  dispatch({ type: 'reset', connection: 'connecting' });
  setEpoch((n) => n + 1);
});
```

session.ts:352-353: `if (this.o.auth.mode === 'cognito' && (await this.refresh())) return true;`. A valid refresh token always succeeds, so the page reconnects, says hello, receives `forbidden` from game-service.ts:621-628 ('this session belongs to another host') and starts again. There is no cap and no backoff.

Playwright probe (Cognito config, scripted server that answers host.hello with error code forbidden): `FORBIDDEN LOOP: hellos in 3s = 136 token refreshes = 137`.

- Impact: On the AWS target a host signed in as account B can open a /present?s= or /host/live?s= link for a session owned by account A, for example a co-presenter handed the link. The tab then calls Cognito's /oauth2/token and opens a new API Gateway WebSocket about 45 times a second, indefinitely. It burns the Cognito token-endpoint quota for the whole user pool and pays for WebSocket connections and Lambda invocations, which works against the scale-to-zero cost model. The screen flickers between 'Your sign-in ended' and connecting, with no useful message. The same loop happens whenever the server rejects a freshly refreshed ID token, for example after an audience or issuer misconfiguration. On the VM, 'forbidden' signs the host out with 'Your session ended. Sign in again.', and signing in returns to the same refused page.
- Auditor's suggested fix: Treat 'forbidden' as its own final state, for example `ended: 'forbidden'` with copy such as 'This session belongs to another host account', and never refresh or reconnect for it. For 'unauthorized', allow at most one refresh-and-retry per connection epoch: if the next hello is refused again, stop and show the signed-out state. Add a reducer test and an e2e test for forbidden.

### FA-17 (major) The editor's unsaved-changes warning is bypassed by browser Back/Forward and by Sign out

- Lens: frontend. Files: `apps/web/src/app/routing.ts`, `apps/web/src/screens/edit/EditPage.tsx`, `apps/web/src/ui/HostShell.tsx`, `apps/web/src/auth/session.ts`
- Evidence: The only guards are `beforeunload` (EditPage.tsx:125-135) and HostShell's `onLeave` on its three header links (HostShell.tsx:23-25, 37-47).

routing.ts:61 `private readonly onPop = () => this.emit();` switches routes on popstate with no hook for a guard. beforeunload does not fire for same-document history entries created by pushState.

The Sign out button calls `onSignOut` directly (HostShell.tsx:52) and is not routed through onLeave. `signOut()` calls `dropSession()` (session.ts:367-370), HostGate then renders LoginScreen and the Editor with its draft state unmounts.

- Impact: W1-web-b requires 'Warn before leaving with unsaved changes.' - Auditor's suggested fix: Add a navigation-blocker hook to NavigationStore. - Auditor's suggested fix: After a moderation action, move focus to the next item's button in the same group, or to the group heading if the group is now empty.
